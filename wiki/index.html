Overview

① 项目定位：一座可运行的教学实验室

mini-vllm 不是生产级推理引擎，而是一座「可运行、可阅读、可改造」的教学实验室。 它复刻了 vLLM 的三大核心支柱：PagedAttention 内存管理（省显存）、 Continuous Batching 动态调度（提吞吐）、完整 CPU Transformer 前向（真实可对话）， 并且加载真实模型权重，与 HuggingFace 参考输出数值对齐。

📄

PagedAttention

BlockPool + BlockTable 按需分页管理 KV cache，引用计数支持前缀共享，几乎消除内存碎片。

🔄

Continuous Batching

LLMEngine 的 admit → decode → sweep 三段循环，请求随时进出，KV 块即释即用。

🧠

真实模型前向

Qwen3 架构全实现：RMSNorm / RoPE / GQA / SwiGLU / QK-Norm，与 HF 逐 token 对齐。

🔤

byte-level BPE

纯 Java 分词器 + ChatML/Jinja 对话模板 + 增量 UTF-8 解码，流式输出不乱码。

⚡

SIMD 加速

DotKernel 基于 JDK Vector API 的向量化点积，缺失时自动回退标量实现。

🌐

OpenAI 兼容服务

JDK HttpServer 提供 /v1/chat/completions（SSE 流式）+ 内置 Web 对话页 + 多模型路由。

Core Mechanism Ⅰ

④ PagedAttention：像操作系统分页一样管理 KV cache

vLLM 的核心创新，也是本项目最值得吃透的机制。自回归生成要缓存每个 token 的 K/V 向量； 传统做法按 max_seq_len 为每个请求预留整段连续显存，带来严重的内部碎片与外部碎片， 显存利用率常常只有 20~40%。PagedAttention 的解法是：把 KV cache 切成等大的物理块（block）， 逻辑连续的序列可以物理散落，靠页表（BlockTable）串起来——正是操作系统虚拟内存的思想。

图 4-1　连续预留（左）与分页管理（右）的碎片对比 —— vLLM 显存利用率远高于传统实现的根本原因

decode 阶段：逐 block 累加模拟 PagedAttention kernel

生成阶段只有一个新 token 的 Q，历史 K/V 散落在物理块中。Qwen3Attention.decodePaged 遍历该请求的每个逻辑块做两遍累加——第一遍收集全部 QKᵀ 得分后 softmax，第二遍按权重累加 V：

for (int h = 0; h < nHead; h++) {
    int kvOff = (h / group) * headDim;       // GQA：Q 头 h 读 KV 头 h/group
    // 第一遍：逐 block 算 attention score
    for (int b = 0; b < nBlocks; b++) {
        float[] kBlk = kvMgr.blockK(bt, b);   // 零拷贝拿物理块的 K 数组
        ... 对块内每个有效 token 累加 q·k ...
    }
    Softmax.softmaxInPlace(scores);
    // 第二遍：逐 block 加权累加 V
    for (int b = 0; b < nBlocks; b++) { ... out += score * vBlk[...] ... }
}
三个关键细节：① 真实 CUDA kernel 用 online-softmax 单遍完成，这里为可读性拆成两遍； ② 最后一个 block 可能没填满，tokensInBlock 按 totalTokens − b×blockSize 截断； ③ GQA 下每 token 只存 kvDim = nKVHead × headDim（Qwen3-0.6B 为 1024 而非 qDim 2048），显存与带宽都省 group 倍。

前缀共享：引用计数的用武之地

多个请求若含相同 token 前缀（如相同 system prompt），KVCacheManager.trySharePrefix 按 block 级内容指纹（h = h*131 + token 滚动哈希）命中已缓存块， pool.retain(id) 引用 +1 直接复用，省去这部分 prefill 的计算与存储。 真实 vLLM 用 RadixAttention 前缀树精确匹配；学习版简化为哈希映射， 且当前引擎走全量 prefill 路径，前缀共享是内存层已就绪的能力接口（见 §⑫ 扩展方向）。

Core Mechanism Ⅱ

⑤ Continuous Batching：请求随时进出，batch 始终填满

静态批处理必须等整批全部完成才能返回、才能接新请求，短请求早早算完却要空等最长的那个。 Continuous Batching 把调度粒度降到每生成一个 token：每一步都重新组织当前 batch， 完成的立刻退出、腾出的资源立刻接纳新请求——这是 vLLM 高吞吐的另一半。

图 5-1　静态批处理的空转（上） vs Continuous Batching 的动态组批（下）

三段循环：admit → decode → sweep

核心在 LLMEngine.step()， 一个调度周期即三步。Scheduler 维护 waiting（并发队列，HTTP 线程随时写）与 running（引擎线程独占）两个队列； Sequence 是请求的完整运行时状态：WAITING → PREFILL → DECODE → FINISHED / ABORTED。

图 5-2　admit → decode → sweep 三段循环与 waiting/running 双队列

emitToken：流式输出的两个细节

  • EOS 不外泄：命中停止 token 时直接 return，不把 <|im_end|> 等特殊 token 解码成文本，否则会污染响应与多轮 ChatML 上下文。
  • 增量解码：BPE 分词下，中文/emoji 的多字节 UTF-8 可能被切在两个 token 里，IncrementalDecoder 缓冲不完整字节，只输出可完整解码的片段，避免流式乱码 ?。

一个具象例子（maxNumSeqs = 2，提交 5 个请求）

step 1:   admit R0,R1（并发满），各 prefill 出首 token；R2~R4 在 waiting 等
step 2~k: R0,R1 各 decode 1 token
step k:   R0 命中 EOS → sweep 释放其 KV block → running=[R1]
step k+1: admit R2（复用 R0 释放的 block）→ running=[R1,R2]
...
最终:     5 个请求全部完成，running 清空（LLMEngineE2ETest 验证此场景）
与真实 vLLM 的差异：decode 途中显存不足时，学习版直接置 ABORTED 不做抢占； 真实 vLLM 会 preemption（把某些请求的 KV cache swap 到 CPU 或 recompute）。多请求 decode 也是逐个串行前向， 而非真正的 batched GEMM。
Model Computation

⑥ Transformer：Qwen3 五大特性的纯 Java 实现

mini-vllm 有两套平行的 LlmModel 实现： Qwen3Model （RMSNorm + RoPE + GQA + SwiGLU + QK-Norm，真实对话）与 TransformerModel （LayerNorm + 学习式位置嵌入 + MHA + GELU-MLP 的 GPT-2/3 微模型，无权重验证流程用）。 两者共享同一套 math 算子与 PagedAttention KV cache。

Memory Management

⑦ KV Cache 内存管理：按需分配、引用计数回收

§④ 讲「attention 怎么用 cache」，这里讲「cache 的内存怎么管」。 三个设计支柱：按需分配（只在容量不足时申请新块）、懒创建（块数组首次 allocate 才创建）、 引用计数回收（归零才真正归还，支持共享；LIFO 归还利于缓存局部性）。

按需分配 ensureCapacity

int needed = (requiredTokens + blockSize - 1) / blockSize;
while (bt.numBlocks() < needed) {
    int id = pool.allocate();
    if (id < 0) return false;  // 池满 → 调度器阻塞新请求
    bt.append(id);
}

prefill 按 promptLen 分配，decode 按 curIdx+1 增量扩容。返回 false 是显存不足信号：admit 时回滚等待，decode 时置 ABORTED。

引用计数回收 release

KVBlock b = blocks[blockId];
b.refCount--;
if (b.refCount == 0) {
    freeList.addFirst(blockId);  // LIFO 归还
    usedBlocks--;
} else if (b.refCount < 0)
    throw new IllegalStateException("引用计数下溢");

共享块（前缀共享）被多请求指向时，只有最后一个释放才回收；下溢直接抛异常，帮学习期尽早暴露重复释放 bug。

显存占用估算（Qwen3-0.6B 默认参数）

bytes     = numBlocks × blockSize × kvDim × 2(K和V) × 4(float)
blocksPerSeq = ceil(maxSeqLen / blockSize)          = ceil(2048/16) = 128
numBlocks    = max(1024, maxNumSeqs × nLayer × blocksPerSeq) = max(1024, 2×28×128) = 7168
单块 = 16×1024×2×4 = 128 KB  ⇒  总计约 7168 × 128 KB ≈ 0.9 GB（满并发不 OOM）

注意 KV cache 按层独立（每层一张 BlockTable），所以公式乘 nLayer。想降内存可调小 --max-seq-len、--max-seqs 或 --num-blocks，或用 --kv-cache-dtype int8 把容量与带宽降到约 1/4。

Weight Loading

⑧ 权重加载：safetensors 解析、五种精度、自动下载

PyTorch 的 .pt/.bin 是 pickle 格式，纯 Java 几乎无法安全解析；而 safetensors 用「明文 JSON header + 裸张量数据」，格式极简，非常适合零依赖解析——这正是项目选它作为权重载体的原因。

图 8-1　safetensors 文件布局、分段读取策略与 BF16/F16 → F32 转换

五种权重常驻精度

精度常驻方式堆需求（Qwen3-0.6B）适用场景
f32BF16→F32 展开进堆约 3GB（磁盘的两倍）默认，数值精度最高
bf16short[] 位表示常驻堆，SIMD 直接消费约 1.5GB0.6B 小模型在 Apple Silicon 上实测最快
int8 / int4per-group 对称量化块常驻堆约 0.7GB / 0.4GB4B+ 大模型的内存可行性
mmap权重不落堆：FileChannel.map 映射进地址空间，OS 按需调页数百 MB（行缓冲 + KV）物理内存装不下模型时（512MB 堆即可跑 1.5GB 模型）

mmap 模式：页缓存承载权重

MmapWeights.open 对每个 safetensors 分片调用一次 FileChannel.map(READ_ONLY, 0, size)——只建页表不读数据， 1.5GB 模型映射耗时 0.0s；之后每次访问触发缺页中断，OS 从磁盘调入 4KB 页进页缓存，内存紧张时自行回收冷页。 这正是 llama.cpp / vLLM 加载大模型的方式。

图 8-2　mmap 权重数据流：磁盘 → 页缓存 → 行缓冲 → SIMD 内核

加载即校验：三重防线

  • 形状校验：每个张量长度必须等于期望的 out×in（Qwen3Loader.get）；
  • 全量消费：所有张量必须被装配消费（tied 下容忍多余的 lm_head.weight）；
  • 参数量校验：numParameters() 必须与按配置公式计算的期望值一致（Qwen3-0.6B ≈ 596M）。

模型自动下载与多模型家族

ModelDownloader 按四级顺序解析模型位置（命中即返回）：项目内 ./models/<name> → HF 缓存 → mini-vllm 本地缓存 → 在线下载 （ModelScope 优先、HF 兜底）。可靠性设计：.part 临时文件 + 原子改名、Range 断点续传、 .part.url 记录来源镜像（跨镜像不续传避免损坏文件）。

模型家族通过 ModelFamily SPI 扩展（META-INF/services 注册）：当前支持 Qwen3Family 与 LlamaFamily—— 家族差异收敛在 ModelConfig（qkNorm 按 model_type 判定、rope_scaling 解析 llama3 参数）， 模型骨架复用同一套 Qwen3Model/Qwen3Loader。对话模板由 JinjaChatTemplate（jinja 子集解释器） 渲染模型自带 chat_template，与 jinja2 逐字符对齐。

设计取舍：为什么这样写

零外部依赖

只用 JDK 标准库（含 com.sun.net.httpserver、jdk.incubator.vector），让代码「可阅读、可改造」，不被框架细节淹没。

CPU 逐 block 模拟

牺牲性能换取可读性，让 KV cache 的分页语义清晰可见——教学项目的第一原则。

两套模型并存

Qwen3/Llama 提供真实可对话体验，GPT 微模型提供无权重快速验证，降低学习门槛。

单线程调度

把 Continuous Batching 的 admit/decode/sweep 三段逻辑摊平在一个 step() 里，一眼看懂。

Learning Path

⑫ 学习路径：从跑起来到改得动

图 12-1　五步学习路线

挑战级扩展方向（引擎能力补齐）

  1. 接入前缀共享：trySharePrefix/registerPrefix 已实现但引擎未使用——改造 admit 逻辑让相同 system prompt 复用 KV block；
  2. 实现 preemption：参考 vLLM 做 swap 到 CPU 或 recompute，让长请求在高压下也能完成；
  3. batched 前向：把同一 step 的多个请求 Q 拼成矩阵做真正的 batched GEMM；
  4. 支持新模型家族：仿照 Qwen3Family/LlamaFamily 注册新 SPI，复用 math/memory/core 全部层。

常见误区提醒

  • RoPE 是 half-split 不是交错式——与 HF 对齐时最常见的坑；
  • QK-Norm 顺序是 Norm→RoPE，反了数值就不对；
  • KVCacheManager 的 dModel 字段实为 kvDim——GQA 下每 token 只存 nKVHead×headDim；
  • 默认关闭思考模式——否则短请求容易被 max_tokens 截断在推理中途；
  • EOS token 不外泄——emitToken 遇停止 token 直接 return，避免 <|im_end|> 污染输出；
  • 随机模式输出无意义——仅验证流程，真实对话请用 Qwen3/Llama 模型。
